## 1. 这份手册解决什么

技能库装好之后，最常见的三个问题是：

| 问题 | 在哪里解决 |
|---|---|
| "我该用哪个技能？" | [第 5 节](#5-按我想干什么找技能)按任务查表 |
| "我该给它什么材料？" | [第 4 节](#4-输入怎么准备)输入清单 |
| "它给我的东西能直接用吗？" | [第 8 节](#8-产出物怎么落地)落地标准 |

一个前提认知：**技能不是搜索引擎**。它不会替你想出答案，它把"该怎么想"固化成流程，逼你把缺的信息补齐。你给的材料越具体，产出越具体。

## 2. 安装与卸载

### 2.1 前置条件

- Python 3.9 及以上（只用标准库，无需 `pip install`）
- 一个能读 Markdown 技能的 Agent：WorkBuddy / Claude Code / Codex / Cursor 等
- 无网络依赖，安装过程不联网

### 2.2 三种安装方式

**方式一：全量安装（推荐首次使用）**

```bash
git clone https://github.com/Asaceoo/Product-Manager-puls-skills.git
cd Product-Manager-puls-skills
python tools/install.py install
```

默认目标是 `~/.workbuddy/skills/`（Windows 即 `C:\Users\<你>\.workbuddy\skills\`）。

**方式二：只装需要的**

```bash
python tools/install.py install --only prd-development,user-story,problem-statement
```

适合明确知道自己只用几类技能的人。装 77 个会让 Agent 的技能清单很长，虽然不影响正确性，但每次会话都要加载描述。

**方式三：装到别的 Agent**

```bash
python tools/install.py install --target D:/my-project/.claude/skills
python tools/install.py install --target ~/.codex/skills
```

只要那个目录是 Agent 扫描技能的路径即可。不确定路径时，先 `--dry-run` 看计划：

```bash
python tools/install.py install --target <路径> --dry-run
```

### 2.3 命名冲突

目标目录已有同名技能时，默认**跳过不覆盖**，并在输出里列出跳过清单。

```bash
python tools/install.py install --force      # 明确要求覆盖时才加
```

判断依据：如果你之前装过上游版本（`deanpeters/Product-Manager-Skills`），同名目录会被跳过。想用本仓库的修复版，就加 `--force`。

### 2.4 卸载

```bash
python tools/install.py list          # 确认装了什么
python tools/install.py uninstall     # 按安装记录移除
python tools/install.py uninstall --dry-run   # 先看会删什么
```

**卸载只删安装记录里的技能**，不会碰你自己写的或其他来源的技能。安装记录文件是目标目录下的 `.pm-skills-installed.json`。

### 2.5 验证装好了

```bash
python tools/install.py list
```

正常输出形如：

```
包版本 v1.0.0  安装于 2026-10-26T16:40:12+08:00
目标目录 C:\Users\<你>\.workbuddy\skills
记录 77 个，缺失 0 个
  - prd-development
  - ...
```

若"缺失"不为 0，说明有目录被手工删过，重新 `install --force` 即可。

## 3. 三种调用方式

### 3.1 自然语言（最常用）

直接描述你要什么，Agent 按 `description` 里的 `Use when …` 匹配。

> 「帮我评估一下这个功能值不值得投人做。」

会命中 `feature-investment-advisor`（描述里有 `Use when evaluating whether a feature is worth building`）。

这类调用的关键：**把你手上的材料一起贴进去**。技能会识别已给的信息并跳过对应提问。

### 3.2 斜杠命令

支持斜杠的 Agent（Claude Code、WorkBuddy 等）可以直接点名：

```
/prd-development 自助开通工作区
/user-story 邀请队友流程
```

`argument-hint` 字段决定斜杠后面提示什么参数。本仓库 77 个技能全部带该字段。

### 3.3 显式指定（最可控）

不确定会命中哪个时，直接说技能名：

> 「用 `swot-analysis` 分析我们公司，范围是免漆门产线，决策背景是明年是否扩产。」

这种写法还有一个好处：**技能内引用的其他技能不会被误触发**。工作流型技能（`prd-development` 等）会编排多个下游技能，显式指定可以避免中途跑偏。

### 3.4 三者怎么选

| 情况 | 用哪种 |
|---|---|
| 说得出要什么结果 | 自然语言 |
| 熟悉技能名，参数清楚 | 斜杠命令 |
| 结果重要、要严格控制流程 | 显式指定 + 补材料 |

## 4. 输入怎么准备

### 4.1 通用清单

技能开头都有 `## Input` 段落，写明"最好有什么"和"还有什么也有用"。通用规律：

| 材料 | 为什么值钱 | 没有会怎样 |
|---|---|---|
| 真实数字（转化率、留存、工单量） | 支撑结论，避免"感觉" | 技能会标 `假设`，结论降级 |
| 用户原话（访谈、客服记录） | 让问题陈述有据可查 | 问题陈述变成主观判断 |
| 决策背景（OKR、预算、时间窗） | 决定取舍尺度 | 建议变成正确但无用的通用答案 |
| 约束（技术、法务、人力） | 排除不可行方案 | 方案落地时被推翻 |
| 已有文档（旧 PRD、周报） | 省掉重复问答 | 多花 5–10 轮对话补齐 |

### 4.2 空手也能开始

所有 workflow 型技能都支持"空手启动"，从问题定义开始逐项收敛。区别只是**收敛轮次变多**。

如果时间紧，至少给三样：**要解决的问题一句话**、**给谁做**、**什么时候要**。

### 4.3 材料怎么贴

不用整理格式，直接粘。技能能处理：

- 会议纪要、Slack/企微聊天记录
- Excel 导出的 CSV、埋点数据截图文字
- 竞品页面复制文本、用户评论
- 上一版文档的片段

贴的时候给一句来源说明即可：

> 「下面是上周三场用户访谈的纪要，共 8 位用户，都是 1-10 人的小团队老板：」
> 「……（粘贴）」

来源说明会进产出物的证据引用。

## 5. 按"我想干什么"找技能

### 5.1 高频任务表

| 我要做的事 | 技能 | 备注 |
|---|---|---|
| 写一份 PRD | `prd-development` | 八阶段，可中途停 |
| 把模糊需求问清楚 | `incoming-request-advisor` | 先拆字面与真实意图 |
| 判断这功能该不该做 | `feature-investment-advisor` | 要收入/成本口径 |
| 给需求排优先级 | `prioritization-advisor` | 先问团队阶段再选框架 |
| 写用户故事 + 验收标准 | `user-story` | Gherkin 格式 |

| 销售要竞品对战卡 | `battle-card-builder` | 每条主张标证据等级 |
| 公司/行业调研 | `company-intel` | 七种透镜 |
| 算市场规模 | `tam-sam-som-calculator` | 强制列假设 |
| 行业结构判断 | `porters-five-forces` | 五力 |

| SaaS 指标体检 | `business-health-diagnostic` | 四维 |
| 准备用户访谈 | `discovery-interview-prep` | 目标/人群/方法 |
| 跑一轮完整发现 | `discovery-process` | 周期较长 |

| 造一个新技能 | `pm-skill-creator` | 对话式设计 |

### 5.2 容易搞混的几组

| 组 | 区别 |
|---|---|
| `swot-analysis` vs `porters-five-forces` vs `pestel-analysis` | SWOT 看**一家公司**内外部；五力看**一个行业**结构；PESTEL 看**宏观**六类因素 |
| `company-research` vs `company-intel` | 前者是**组件**（出一份简介），后者是**工作流**（多透镜深研，耗时长） |
| `competitive-research-snapshot` vs `competitive-intel-watch` | 前者做**首次快照**，后者做**对旧快照的增量**（要先有快照） |
| `user-story` vs `user-story-mapping` vs `user-story-splitting` | 写一条 / 铺一张地图 / 拆一条大的 |
| `pol-probe` vs `pol-probe-advisor` | 前者是**模板**（你已知用哪种），后者帮你**选** |
| `eol-readiness-advisor` vs `eol-process` | 先判断**该不该退**（前者），再执行**怎么退**（后者） |
| `product-lifecycle-plays` vs `lifecycle-play-advisor` | 前者是阶段→打法的**对照表**，后者是**帮你诊断**当前阶段 |
| `customer-journey-map` vs `-workshop` | 前者直接**出图**，后者**带团队走流程** |

### 5.3 什么时候别用技能

- 一句话能说清的事（改个文案、查个定义）——直接问，技能会绕远
- 需要实时数据（今天的股价、当前库存）——技能不联网查数
- 有法律/合规风险的正式文本——技能产出是草稿，必须律师复核

## 6. 13 个主题的用法

每组给：**什么时候用**、**典型问法**、**要准备什么**、**产出是什么**。

### 6.1 市场情报（18）

**什么时候用**：要回答"外面什么情况"——竞品在干什么、行业结构怎么样、市场有多大。

**典型问法**
> 「我们做室内门，帮我看看这个行业的五力结构，重点是新进入者和替代品。」
> 「A 公司上季度降价 30% 还加了两项服务，帮我建个竞品快照，能按季度 diff 的。」

**要准备**：目标公司/市场范围、你的决策背景（为什么现在要这个）、已有的旧资料（有的话直接给，技能会做增量）。

**产出**：带引用出处的分析文档。`swot-analysis` 会收尾给 S-O 进攻策略与 W-T 风险敞口；`battle-card-builder` 出销售可直接用的一页卡；`pricing-packaging-tracker` 出可 diff 的时间序列表格。

**常见误用**：不给范围。说"分析一下竞品"会得到一份泛泛而谈的东西；说"分析这三家，我要决定是否跟进降价"才有决策价值。

### 6.2 PM 交付物（8）

**什么时候用**：要把想法变成工程能接手的文档。

**典型问法**
> 「把这份调研笔记整理成 PRD，我要给研发评审。」
> 「这个 Epic 太大了，帮我按拆分模式拆成能两周内交付的故事。」

**要准备**：问题陈述、目标用户、成功指标（哪怕是暂定的）。写 PRD 时如果连指标都没有，技能会停在这一步要求你先定指标——这是设计意图，不是卡你。

**产出**：套 `template.md` 的完整文档。PRD 含 10 个章节，每章自带填空指导和跨章节一致性检查。

**常见误用**：跳过问题定义直接要方案。`prd-development` 的 Phase 2 不给过，后面所有内容都建在沙上。

### 6.3 财务指标（7）

**什么时候用**：要给"做/不做"算账。

**典型问法**
> 「这个功能要投 3 个人 2 个月，帮我算值不值。」
> 「竞品降价了，我们跟进会怎样？我有 ARPU 和月流失率。」

**要准备**：真实口径的数字。ARPU、转化率、流失率、CAC、毛利结构，有几个给几个。

**产出**：带敏感性分析的评估。`finance-based-pricing-advisor` 会给 ARPU / 转化 / 流失 / NRR / 回本期五个维度的影响区间。

**常见误用**：给"大概""差不多"的数字。财务类技能对输入精度敏感，模糊输入只会得到模糊结论——而且技能会明确标注"因输入不确定，结论仅供参考"，等于白跑。

### 6.4 发现与用户研究（7）

**什么时候用**：还不确定问题是什么，或不确定方案对不对。

**典型问法**
> 「下周要做 6 场用户访谈，帮我设计提纲，用户是中小门窗经销商。」
> 「我怀疑问题不是功能少而是找不到入口，帮我框定一下。」

**要准备**：已知的用户反馈、你的初步假设。

**产出**：访谈提纲（含不该问的问题）、问题框定画布、JTBD 任务清单、机会解决方案树。

**常见误用**：把发现当验证。发现阶段的目标是**找对问题**，不是证明你的方案对。如果心里已有答案，用 `pol-probe-advisor` 设计验证实验更合适。

### 6.5 生命周期终止（6）

**什么时候用**：某条产品线/功能成了负担，要停止投入。

**典型问法**
> 「老款免漆门系列销量掉到 5%，但还有客户在订，要不要停？」
> 「决定停产后，内部怎么通知？销售那边会有阻力。」

**要准备**：销量趋势、存量客户与合同义务、替代方案。

**产出**：go/no-go 评估、分阶段清单（每项有责任人）、分档公告文案、内部 FAQ 与销售话术、干系人沟通顺序。

**常见误用**：只做对外公告不做内部赋能。`eol-internal-enablement` 单独存在就是因为销售和支持没准备好时，公告一发就炸。

### 6.6 职业与领导力（5）

**什么时候用**：晋升准备、面试、新岗位上任。

**典型问法**
> 「我在准备产品经理面试，帮我练一道产品感题：设计一个给老人用的智能门锁 App。」
> 「刚升总监，团队从 3 人变 12 人，前 90 天该干什么？」

**要准备**：你的真实经历（项目、数字、决策）、目标岗位的 JD。

**产出**：结构化口述答案（假设 → 分层 → 痛点 → 方案 → 取舍 → 指标）、过渡期诊断、30-60-90 天计划。

**常见误用**：让技能编经历。这类技能会追问你的真实项目细节，编的答案在面试追问第二层就会崩。

### 6.7 工作坊引导（5）

**什么时候用**：要带一群人开共创会。

**典型问法**
> 「下周三带 8 个人开定位工作坊，2 小时，帮我设计流程。」

**要准备**：参会人角色、时长、要产出的决策。

**产出**：一步步引导脚本，含每步时长、提问、产出物、常见跑偏处理。

**常见误用**：当成"帮我写个议程"。区别是 `workshop-facilitation` 会在每个决策点给编号选项让你选，而不是给你一份通用议程。

### 6.8 验证与实验（5）

**什么时候用**：有个高风险假设，想知道最省钱的验证方式。

**典型问法**
> 「我假设经销商愿意为数据分析付月费，怎么用两周和 5000 块验证？」

**要准备**：假设的具体表述（越具体越能设计实验）、可动用的资源、时间窗。

**产出**：PoL 探针方案（含成本、周期、判定标准、失败后怎么办）。

**常见误用**：假设太笼统。"用户会喜欢"无法验证；"经销商愿意为月度报表付 200 元/月，且至少 5 家签约"才可以。

### 6.9 策略与定位（5）

**什么时候用**：要说清"我们是谁、为谁、凭什么是我们"。

**典型问法**
> 「帮我们写定位陈述，我们做免漆门，客户是三四线城市家装公司。」

**要准备**：目标客户、未被满足的需求、替代方案（含"什么都不做"）、独特能力。

**产出**：Moore 式定位陈述、优先级框架选型建议、战略 Roadmap。

**常见误用**：定位写成宣传语。定位陈述是内部对齐工具，必须能排除掉一些客户——如果一句话能套在任何同行身上，它就不是定位。

### 6.10 干系人与沟通（4）

**什么时候用**：事情推不动，或要向上汇报。

**典型问法**
> 「这个需求是老板转过来的，但我觉得优先级不对，怎么处理？」

**要准备**：涉及的人、各自诉求、你的约束。

**产出**：干系人清单与优先级网格、单个干系人的沟通策略、模糊需求的拆解（字面要求 vs 真实意图）。

**常见误用**：只做"话术"。这类技能先要求你列全干系人与各自利益，话术是最后一步。

### 6.11 AI 与 Agent（3）

**什么时候用**：在做 AI 产品，或在设计 AI 工作流。

**典型问法**
> 「我想用三个 Agent 分别做需求分析、方案生成、评审，这样设计合理吗？」

**要准备**：当前流程、痛点、AI 在其中的位置。

**产出**：AI 就绪度评估（AI-first 还是 AI-shaped）、上下文工程诊断、多 Agent 编排设计（边界、交接协议、监控点）。

**常见误用**：把"多 Agent"当目标。技能会先问"单 Agent 卡在哪"，多数情况下结论是不需要拆。

### 6.12 产品生命周期（2）

**什么时候用**：要判断现在该加大投入、维持、还是准备退。

**典型问法**
> 「我们这条线增长停了但还有利润，该加投入还是准备退？」

**要准备**：增长曲线、利润率、竞争位置、战略权重。

**产出**：阶段诊断 + 打法建议（extend / replace / retire）。

### 6.13 元技能（2）

**什么时候用**：想把这套方法用在自己的领域，造新技能。

**典型问法**
> 「我想做一个'门业安装质量检查'技能，帮我把我的经验结构化。」

**产出**：符合 frontmatter 规范的新技能骨架（含 description 触发语、输入定义、阶段流程、模板）。

## 7. 五个完整走查

### 走查一：从模糊需求到一页决策建议

**情境**：运营总监在企业微信里发来一句"做个积分系统，下周给方案"。

**第 1 步** — 拆解需求

> 「用 `incoming-request-advisor` 拆解这条消息：『做个积分系统，下周给方案』。背景是我们是门业 B 端，客户是经销商，目前没有任何会员体系。」

产出：字面要求（做积分系统）、可能真实意图（提升复购 / 应对竞品 / 老板想法）、需要回问的 3 个问题、可先做的低成本动作。

**第 2 步** — 框定问题

> 「用 `problem-framing-canvas`，问题是：经销商复购率连续两季下滑 8%。」

产出：问题框定画布，含"我们以为的问题"与"证据支持的问题"的差异。

**第 3 步** — 判断优先级

> 「用 `prioritization-advisor`，团队 5 人，本季度还有两个必做项，判断积分系统该不该现在做。」

产出：框架选型理由 + 排位建议。

**最终交付**：一页纸，含问题证据、三个候选方案、成本估算、建议顺序。这比"好的我来做"有用得多。

---

### 走查二：材料散落时写 PRD

**情境**：手上有 8 份访谈纪要、一份 OKR、37 条客服工单，要出 PRD。

**第 1 步**

> 「用 `prd-development` 写 PRD，主题是"经销商自助下单"。以下是材料：」
> （依次粘贴 OKR、访谈摘要、工单高频问题）

技能会：识别已有材料 → 跳过对应提问 → 只问缺的（通常是成功指标口径与范围边界）。

**第 2 步** — 中途检查

技能推进到 Phase 6（成功指标）时会要你定主指标。这一步不要跳过：

> 「主指标：经销商自助下单占比，现在 12%，目标 40%，3 个月。」

**第 3 步** — 收尾自检

技能结尾会给自检：最强章节、最弱章节、待验证假设 Top 3、建议下一步。

**最终交付**：10 章 PRD + 一份"送评审前必须补的三件事"清单。

---

### 走查三：竞品降价应对

**第 1 步** — 建可对比基线

> 「用 `pricing-packaging-tracker` 建 A/B/C 三家竞品的定价快照，含产品分层、价格、包含服务、折扣政策。」

**第 2 步** — 出销售武器

> 「用 `battle-card-builder` 出 A 公司的对战卡，重点回应'他们比我们便宜 30%'。」

**第 3 步** — 算账

> 「用 `finance-based-pricing-advisor` 算我们跟进降 20% 的影响。当前 ARPU 4800 元/年，年流失率 18%，毛利率 32%。」

**最终交付**：定价时间序列 + 一页对战卡 + 降价影响区间（含最坏情况）。

---

### 走查四：面试答题训练

**情境**：准备产品经理面试。

> 「用 `product-sense-interview-answer`，题目是"设计一个给装修公司用的材料管理系统"。我的背景是门业管培生 2 年，做过经销商管理。」

技能会按"澄清 → 用户分层 → 痛点排序 → 方案 → 取舍 → 指标 → 风险"推进，并在每步要求你给**真实经历支撑**。

**产出用法**：把每一轮的答案整理成口述稿，重点背"取舍理由"——面试官追问的永远是取舍。

---

### 走查五：判断要不要退市

> 「用 `eol-readiness-advisor`，评估老款免漆门系列是否退市。销量从月 800 套掉到 40 套，仍有 6 家老客户在订，其中 2 家有年度合同。」

技能会做 go/no-go：合同义务、替代方案、客户迁移成本、内部影响、财务影响。若结论是"退"，接着：

> 「按 `eol-process` 排执行计划，6 个月窗口。」

产出：分阶段计划 + 清单（每项有责任人）+ 公告文案分档 + 内部赋能材料 + 干系人沟通顺序。

## 8. 产出物怎么落地

### 8.1 直接可用 / 需要加工

| 产出类型 | 可直接用 | 必须加工 |
|---|---|---|
| 访谈提纲、工作坊脚本 | ✅ | — |
| 清单类（EOL checklist、story map） | ✅ | 补责任人 |
| PRD、定位陈述 | 结构可用 | 补真实数据、删掉标了 `假设` 的推断 |
| SWOT、五力、PESTEL | 框架可用 | 每条主张都要能指到证据 |
| 财务测算 | 公式可用 | 换成你的真实口径重算 |

### 8.2 三种标记必须处理

技能会用三种方式标记不确定：

| 标记 | 含义 | 你怎么处理 |
|---|---|---|
| `假设`（Assumption） | 合理但未验证 | 找数据验证，或在文档里显式标为待验证 |
| `待验证`（Open Question） | 未知，需要调研 | 变成待办事项，指派人和时间 |
| 证据等级（如 `[unverified]`） | 来源强度不同 | 引用前核对原链接 |

**不要删掉这些标记就交出去**。它们的价值在于让评审者知道哪里是硬结论、哪里是推断。

### 8.3 进评审会

PRD / 策略类产出进评审前，至少做完三件事：

1. 把所有 `假设` 换成数据，或显式声明"这是假设，需要 X 周验证"
2. 补上"不做会怎样"——多数评审卡在这个问题
3. 明确要评审者做什么决策（批准预算 / 选方案 / 只是告知）

### 8.4 进简历 / 面试

技能产出不能直接当简历素材。可用的部分是**结构**：

- 用 `problem-statement` 的结构重写你的项目描述：谁被卡住、想做什么、卡在哪、你做了什么、结果如何
- 用 `product-sense-interview-answer` 的框架组织面试答题
- 用 `feature-investment-advisor` 的维度（收入影响、成本、ROI）讲清你做过的一个取舍

**数字必须是你自己的真实数据**。技能不会替你编，你也别编。

## 9. 常见问题

**Q：装了 77 个，会不会让 Agent 变慢或选错？**

技能描述会进上下文，确实增加 token。但 `description` 都经过压缩（平均 150 字符），77 个约 12K 字符。如果在意，用 `--only` 只装常用的 10–15 个。

选错的风险主要来自名字相近的几组，[5.2 节](#52-容易搞混的几组)给了区分表；也可以在提问时直接点名技能。

**Q：技能和直接问 AI 有什么区别？**

直接问得到的是"一次成型的回答"，好坏取决于你这次怎么问。技能给的是**固定流程**：同样的技能，换人用、换时间用，推进阶段和产出结构都一样。差别在可复用性和可审查性。

**Q：为什么它一直问我问题，不能一次做完？**

这是 `interactive` 类型（29 个）的设计：一步一问，每步给编号选项，方便你快速回应。想快就直接给全部信息，或说"按你的最佳判断继续，缺的标假设"。

**Q：能离线用吗？**

技能本身是本地的，不联网。但部分技能（市场情报类）会要求 Agent 检索公开信息，那一步依赖你所用 Agent 的联网能力。

**Q：产出是中文还是英文？**

技能正文是英文（方法论原文），但你用中文提问，Agent 会用中文产出。框架名、字段名会保留英文原文（如 `jobs-to-be-done`），便于对照原文献。

**Q：能改技能内容吗？**

可以，`SKILL.md` 就是纯文本。改完记得：

```bash
python tools/manifest.py generate   # 重建清单
python tools/validate.py            # 确认一致性
```

直接改已安装的副本（`~/.workbuddy/skills/`）不会影响仓库；想长期保留改动就改仓库里的 `skills/` 再重新安装。

**Q：为什么有些技能有 `template.md` 和 `examples/`，有些没有？**

`workflow` 和 `component` 类型通常带模板（要填的东西多）；`interactive` 类型靠对话推进，模板以对话结构存在。文件构成见 `MANIFEST.json` 里每个技能的 `files` 字段。

**Q：许可证能商用吗？**

**不能**。CC BY-NC-SA 4.0 明确禁止商业使用。内部培训、个人学习、非营利可用；对外售卖或作为商业交付物的一部分需原作者授权。

## 10. 更新与版本

### 10.1 三套版本号

| 版本 | 位置 | 递增时机 |
|---|---|---|
| 包版本 | `VERSION` / `versions.json` → `package` | 技能内容或工具变更 |
| 用户手册 | `versions.json` → `user_manual` | 本文件改动 |
| 技术手册 | `versions.json` → `tech_manual` | 技术手册改动 |

三者独立计数，但本仓库的 `build.py` 会在发布时一起递增，保证文档与代码版本对齐。

### 10.2 检查你装的是哪版

```bash
cd Product-Manager-puls-skills
python tools/version.py show
python tools/install.py list
```

两者版本号应一致。不一致说明装的是旧版，`install --force` 更新。

### 10.3 升级流程

```bash
git pull
python tools/install.py install --force
```

`--force` 会覆盖已装技能。如果你改过已安装的副本，先备份。

### 10.4 查看改了什么

```bash
git log --oneline -20
cat CHANGELOG.md
```

`CHANGELOG.md` 由 `tools/build.py` 每次发布自动追加，与 release 一一对应。

## 11. 自己改技能

77 个技能不可能刚好覆盖你的业务。改一个比造一个容易得多，造一个比想象中简单。

### 11.1 先查有没有重叠

```bash
./scripts/find-a-skill.sh --keyword 门业
```

输出按正文命中次数排序。如果已有技能覆盖了七成，**扩展它比新建一个更好**——两个语义重叠的技能会让 Agent 路由出错。

### 11.2 改现有技能

```bash
# 1. 直接编辑（改你安装的那份，或改仓库里的副本）
#    ~/.workbuddy/skills/<name>/SKILL.md

# 2. 改完必须校验，否则清单摘要会对不上
python tools/manifest.py generate
python tools/audit.py
python tools/validate.py
```

`audit.py` 会告诉你哪条规则没过，附带文件与行号。常见三类：

| 报错 | 原因 | 怎么修 |
|---|---|---|
| `C1 description 缺少触发语` | 你改了描述但没写 `Use when …` | 补一句"什么时候用" |
| `B13 正文一级章节少于 2 个` | 删章节删过头了 | 至少保留 Input / Application |
| `B19 引用的脚本不存在` | 写了个不存在的脚本路径 | 改路径或删掉那段 |

### 11.3 造新技能

```bash
# 从一份文档生成骨架（最省事）
./scripts/add-a-skill.sh 我的质检经验.md --name installation-qc --type workflow --theme eol-transition

# 或者从零起
./scripts/build-a-skill.sh --name installation-qc --type interactive --theme workshops-facilitation
```

生成的骨架里有括号占位，需要你填。填完：

```bash
# 检查单个技能
./scripts/test-a-skill.sh --skill installation-qc

# 检查元数据
python scripts/check-skill-metadata.py skills/installation-qc/SKILL.md

# 检查 Agent 能不能选对
python scripts/check-skill-triggers.py skills/installation-qc/SKILL.md --show-cases
```

### 11.4 七个运维命令

| 命令 | 用途 | 什么时候用 |
|---|---|---|
| `find-a-skill.sh --keyword X` | 搜技能 | 造新技能前查重叠 |
| `check-skill-metadata.py <file>` | 校验 frontmatter | 改完 frontmatter 后 |
| `check-skill-triggers.py <file>` | 检查触发语与场景 | 担心 Agent 选不中时 |
| `test-a-skill.sh --skill X` | 单技能全检 | 改完一个技能后 |
| `zip-a-skill.sh --skill X` | 打包单个技能 | 想单独分发某个技能 |
| `generate-catalog.py` | 重建目录索引 | 增删技能后 |
| `check-dist-freshness.py` | 检查包是否过期 | 发布前 |

它们都是薄壳，实际实现在 `scripts/skillctl.py`，全部只用标准库。

### 11.5 打包与发布

```bash
./scripts/build-dist.sh          # 等价于 python tools/build.py
```

会依次做：版本递增 → 重建清单 → 三视角审查 → 清单校验 → 写 CHANGELOG → 出 zip。
任何一环失败都不会产出包。
